# v0.3.27 — устойчивость чтения продаж Saby

Наблюдаемая ошибка: HTTP 500 на /retail/order/list для точки 5598 за 22.10.2026.
Сам статус не подтверждает ни антибот-блокировку, ни определённую причину на стороне Saby.
В прежнем клиенте именно HTTP 500 не входил в список повторяемых ошибок чтения продаж.

Для GET /retail/order/list теперь:
- до четырёх попыток при 500/429/502/503/504 и временных сетевых ошибках;
- последовательные запросы в пределах процесса, не чаще одного старта за 3 секунды;
- распознавание ранее наблюдавшегося error.details «Метод вызывается слишком часто»;
- при этом признаке ожидание не меньше 120 секунд плюс запас, либо дольше по указанному сроку;
- числовой Retry-After соблюдается; нераспознанный заголовок останавливает попытки, чтобы не повторять раньше срока;
- ожидание свыше 600 секунд не выполняется автоматически: ошибка возвращается вызывающему коду;
- диагностический код UPSTREAM_ERROR или RATE_LIMIT, HTTP-статус, точка, окно, число попыток без исходного тела/токенов;
- исчерпание попыток остаётся ошибкой; отмена не перехватывается как успех.

Авторизация и API каталога используют прежнюю логику. Запись продаж, upsert, бизнес-даты,
пересборка смен, сверка и схема БД не изменены. Сериализация действует для клиента продаж
в одном процессе и не координирует другие экземпляры приложения или внешние обращения аккаунта.
Загрузка может идти медленнее. Другие уже завершённые блоки данных не удаляются.

## Порядок проверки на сервере

1. Установить архив. Для контролируемой ручной проверки временно выключить
   AUTO_SYNC_ENABLED=false и AUTO_SYNC_ON_START=false, перезапустить приложение.
   Убедиться, что нет отдельно работающего backfill/второго экземпляра загрузчика.
2. В боте выполнить /sync 1. Эта команда загружает текущий календарный день по местному
   времени приложения. На 23.10.2026 это нужный день примера. На другую дату сначала
   выбрать подходящий диапазон по существующим командам, не считать /sync 1 фиксированной датой.
3. Дождаться итогового OK или ошибки; при постоянной 500 прислать новый диагностический код.
4. Проверить /sales 2026-10-23 2026-10-23 398, затем:

```text
python -m scripts.diagnose_sale --number 25522 --date 2026-10-23 --point-id 398
```

5. После проверки вернуть автозагрузку в согласованный режим.

Старые записи RUNNING автоматически не исправляются: статус сам по себе не доказывает
живой процесс. Даже после успешного нового запуска прежний RUNNING может оставлять
предупреждение качества. Это отдельная задача диагностики; массовое обновление всех
RUNNING на OK или удаление истории не допускается. Эта сборка не заявляет решения
всех возможных причин HTTP 500 и не подтверждает полноту источника.

Бонусы по продаже 25522 ещё не подтверждены: ранее найденный внутренний ID оказался
другой июльской продажей. Нужно найти октябрьский номер после успешной загрузки.
Сервер и рабочая база при подготовке архива не изменялись.
