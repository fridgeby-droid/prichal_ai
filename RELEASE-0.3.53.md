# Причал AI 0.3.53 — управленческие возможности и проверка действий

## Что добавлено

**Допродажи.** Общие правила основной и целевой группы по стабильным ID, выбор из локальных товаров. Доля = уникальные покупки с обеими группами / покупки основной группы. Отдельные разрезы: магазин и учётка/смена/день недели. Есть сопоставимая база остальных учёток и объём выборки; менее 30 покупок основной группы у учётки или у остальных — LOW_SAMPLE. Эти разрезы не складываются. Покупки без целевого товара — наблюдение, не доказанная потерянная выручка. Явные модификаторы учитываются как факт присутствия, их сумма не прибавляется к товарной выручке.

**Разбор средней покупки.** Сценарий объединяет разложение суммы уникальных продаж на число покупок и среднюю покупку, структуру корзины и разложение сумм товарных строк по количеству и средней фактической цене. Стабильные ID и единицы сопоставляются отдельно, неизвестная сторона остаётся неизвестной. Цена включает влияние скидок/состава продаж и не является прайсом. Суммы товарных строк, уникальных продаж и платежей не смешиваются. Разделы читаются отдельно; ошибка одного раздела явно видна.

**Ассортимент.** Показывает товар, который продавался в базовом периоде в выбранном магазине, не имеет текущих записей здесь, но продаётся сейчас в других магазинах. Вывод — проверить наличие/выкладку; подтверждённых остатков нет. Возвраты исключены. Объём наблюдаемых дней магазина показан отдельно.

**Возможное замещение.** Динамика двух подтверждённых групп товаров и их объединения за текущий и базовый периоды. Правило задаётся по ID. Одновременный рост одной группы и снижение другой не доказывают причинное замещение.

**Индивидуальная задержка визита.** Минимум 4 разных дня посещений. Обычный интервал — медиана промежутков между наблюдаемыми днями; сигнал — задержка не менее двух таких интервалов. Список упорядочен по сумме наблюдаемых покупок за последние 90 дней, затем по относительной задержке. Это не вероятность ухода, прибыль или пожизненная ценность. Для магазина история ограничена этим магазином, для сети — всей сетью.

**Возвращение клиентов.** Существующий расчёт событий возвращения после 30+ дней теперь доступен кнопками, включая повторный визит за 30 дней после возвращения. При незавершённом окне показатель остаётся неизвестным. Добавлена кнопка ценности клиентских групп.

**План внимания.** Три крупнейших отрицательных изменения выручки в день среди сопоставимых по локальному покрытию магазинов. Вывод — где начать разбор. Пропуски не ранжируются как нулевые продажи. Это наблюдаемые изменения, не доказанные причины.

**Действие → проверка.** В задаче можно записать описание выполненного действия и текущую дату фиксации. Новый показатель — доля допродаж в процентах. Правило целиком копируется в задачу; дальнейшая правка общего правила не меняет её критерий. Абсолютное изменение доли — процентные пункты; порог роста задачи — относительный процент. Сравнение до/после не доказывает эффект действия. Запись действия не означает, что помощник выполнил его в магазине.

## Где искать кнопки

- Обзор сети → **Три магазина для внимания**.
- Товары → **Допродажи**, **Товары без продаж здесь**, **Возможное замещение**, **Правила допродаж и замещения**.
- Покупки → **Разбор средней покупки**, **Цена и количество товаров**.
- Клиенты и бонусы → **Клиенты с задержкой визита**, **Вернувшиеся клиенты**, **Ценность клиентских групп**.
- Задачи → Новая → показатель **Доля допродаж** → правило → срок → **Добавить описание действия** → подтверждение.
- Данные → **Источники и ограничения**.

Для новых детальных отчётов есть CSV всей выборки и страницы. Для составного разбора и плана внимания полный единый CSV не предлагается; выгружайте соответствующий детальный отчёт.

## Настройка правила

Товары → Правила → Допродажа / Возможное замещение → название → поиск основного товара → точный вариант с ID → поиск целевого товара → точный вариант → подтверждение.

Кнопочный мастер создаёт пару товаров. Для групп до 50 ID в каждой стороне можно использовать помощника: сначала поиск кандидатов, затем явное подтверждение состава. Группы не должны пересекаться. Одинаковое имя обновляет правило, что явно указано перед сохранением. Правила общие для разрешённых пользователей, изменение доступно только в личном чате. До 50 правил каждого вида. Файловые правила совместимы; запись PostgreSQL с тем же именем имеет приоритет.

Поиск обычных товаров идёт по локальным товарным строкам. Модификаторы дополнительно ищутся в последних 200 сохранённых продажах; это ограниченная выборка. Если модификатор не найден, это не означает его отсутствия: уточните ID из детального отчёта модификаторов. Суммы, телефоны, карты и сырой JSON в результат поиска не передаются.

## Примеры вопросов

> Где реже продают пакет вместе с выбранным товаром? Используй правило «Пакет».

> Разбери среднюю покупку Батумской: октябрь к сентябрю 2026. Отдели количество и среднюю цену товаров.

> Какие товары продавались в Батумской в сентябре, но в октябре записей нет, хотя в других магазинах они продаются?

> Кто из клиентов обычно приходил регулярно, но задержался с визитом на 31 октября 2026?

> Кто вернулся после перерыва и пришёл снова в течение 30 дней?

> Какие три магазина стоит проверить по итогам октября к сентябрю 2026?

> Начали предлагать закуску в дневной смене Батумской. Запиши действие и через неделю проверь долю допродаж по правилу «Закуска».

## Ограничения источников

Подключение новых внешних источников в эту сборку не входит: нет подтверждённых данных счётчиков, остатков/поступлений и себестоимости. Для них добавлен явный перечень требуемых данных; конверсия и маржа не выдумываются. Существующая интеграция Core сохранена, но эти сравнения по-прежнему используют учётки Saby, не фактический график сотрудников. Для реальных показателей потребуются соответствующие источники и проверка привязок.

## Установка и проверки

Обычное обновление архива, без миграции продаж и без новой загрузки Saby. Сохранённые задачи, подписки и настройки не сбрасываются. Правила и описания действий сохраняются в существующей PostgreSQL app_meta. Откройте свежее меню после обновления.

Проверьте: создание правила с подтверждением; отчёт допродаж и CSV с теми же фильтрами; отсутствие двойного подсчёта разных разрезов; клиентскую задержку; товарный разбор с отсутствующей стороной; создание задачи по доле допродаж с описанием действия. При пустых правилах должен быть RULES_REQUIRED, а не нулевые допродажи.

Локальные тесты используют подставные данные. Подключение к боевой БД, фактические Telegram-ответы и трактовки модели нужно проверить после установки.
