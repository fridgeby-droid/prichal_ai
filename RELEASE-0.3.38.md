# Причал AI v0.3.38 — установка и проверка

Проверка перед упаковкой: 368 локальных тестов пройдены; импорт веб-приложения v0.3.38 и регистрация get_advanced_report в агенте проверены. Архив дополнительно проверяется по CRC и побайтовому совпадению с исходниками; рядом публикуется SHA256.

Сборка включает предыдущий несобранный пакет (CSV, карточку клиента, сравнение товаров, диагностику платежей, облегчённую проверку загрузки, повторы изображений) и обе очереди расширенной аналитики. Никакой новой загрузки Saby для отчётов не требуется. Миграция/очистка старых данных не нужна. Ключи, настройки Timeweb и API Core сохраняются.

## Установка

Загрузить ZIP в Bothost привычным способом и дождаться запуска приложения. Не запускайте вторую бонусную загрузку, пока работает первая. Перезапуск приложения может прервать процесс загрузчика; уже сохранённые ответы остаются. После установки сначала проверьте `python -m scripts.bonuses plan`, затем продолжайте `python -m scripts.saby_data resume`, только если предыдущий загрузчик больше не работает. Архив не содержит секретов; переменные окружения остаются на сервере.

Проверка версии:

```text
python -c "print(__import__('app.version', fromlist=['APP_VERSION']).APP_VERSION)"
```

Ожидается 0.3.38. Архив подготовлен локально; сервер не обновлялся автоматически. Тесты локальные, без производственной PostgreSQL и без обращений к Saby.

## Допродажи и замещение: один раз задать правила

Файл `data/analytics-rules.json` содержит пустые списки: реальные соответствия товаров нельзя угадывать. Используйте стабильные ключи из /itemqty или /products (`id:...` либо `uuid:...`). Сохраните свой файл правил при следующих обновлениях приложения: это конфигурация внутри сборки, не таблица БД.

Образец структуры (ID примера заменить реальными; не готовое правило для сети):

```json
{
  "crosssell": [
    {"id": "beer_snack", "base": ["id:123"], "target": ["id:456", "id:789"]}
  ],
  "substitution": [
    {"id": "beer_alternatives", "base": ["id:123"], "target": ["id:456"]}
  ]
}
```

base — товары основной покупки или исходная группа; target — дополнение или альтернативная группа. Группы непустые и не пересекаются. Для нескольких правил используются разные id. Один чек с несколькими товарами группы считается один раз.

```text
/analytics crosssell 2026-09-01 2026-09-30 point=398
/analytics substitution 2026-09-01 2026-09-30 previous_start=2026-08-01 previous_end=2026-08-31 point=398
```

Без правил ожидается RULES_REQUIRED. Сравнение учёток также добавляет доли допродаж, когда эти правила настроены. Новые товары не включаются в правила автоматически. В допродажах можно указать ID модификатора из /modifiers: вложенные позиции с явным IsModifier=true читаются из сохранённой продажи, отказанные/возвратные исключены. Их суммы не прибавляются к продаже. В замещении используются только обычные товарные строки: неизвестные суммы модификаторов не подменяются нулями.

## Как трактовать новые показатели

- Регулярность: дни с продажами товара / дни с наблюдаемыми продажами магазина. Показывается также календарная длительность. Это не дни наличия на полке.
- Локальный ассортимент: доля суммы товара в товарных строках магазина / его доля по всей сети. Даже при point=398 база сравнения — сеть. Нет контроля остатков и сезонности; показатель не означает гарантированный спрос.
- Структура покупки: количество разных товаров (1, 2–3, 4+, неизвестно/пусто) и сумма (<300, 300–999.99, 1000+ ₽). Разрезы независимые.
- Переходы: последовательные дни визита клиента в разные магазины. Если за день несколько магазинов, этот переход исключается как неоднозначный. При point дополнительно число старых клиентов магазина, которые в выбранном периоде покупали только в других точках. Это не доказательство окончательного ухода. Для анализа читается история всей сети.
- Возвращение после перерыва: события после 30–59, 60–89, 90+ дней; один клиент может попасть несколько раз. Повтор в следующие 30 дней вычисляется только при закрытом окне, иначе неизвестно.
- Ценность: непересекающиеся группы — впервые наблюдаемые, остальные с ≥4 днями посещений, редкие со средней покупкой ≥1000 ₽, остальные. Новые имеют приоритет. Доля суммы только среди известных клиентов. Это не LTV и не прибыль.
- Концентрация: доля первых 1/5/10/20 клиентов и товаров. Клиентский знаменатель только покупки с Customer, товарный — строки со стабильным ID. Анонимные покупки не приписываются одному клиенту.
- Сравнение учёток: один магазин, день недели, DAY/NIGHT; средняя покупка и разные товары на покупку, база — другие учётки этой же группы. Нет данных о реальных часах работы и трафике, поэтому это не рейтинг сотрудников и не расчёт зарплаты.
- Бонусы: актуальный сохранённый OK ответ, fingerprint совпадает. Группы взаимоисключающие: без Customer, неподтверждённые, со списанием, к начислению, ответ без положительной операции. При списании и начислении одновременно чек в группе списания, обе известные суммы сохраняются. bonusInc — к начислению, не доказательство проведённого начисления; availableBonusInc не суммируется. Повторные визиты клиента считаются по любым его покупкам внутри периода; клиенты могут встречаться в разных группах. По дням показано покрытие и доля покупок с известным списанием. Не переводим баллы в рубли и не считаем долю баллов в выручке без подтверждённого курса. Зависимость поведения от бонусов не доказывает эффект программы.
- Все суммы нового пакета — TotalPrice уникальных продаж или явно подписанные суммы строк, **не платёжная выручка**. Возвраты не вычитаются из продаж. Не складывать разные разделы. РЦ исключён, полнота источника не подтверждается отчётом.

## Трафик

В архив включена команда `scripts.traffic` для проверки файла и нормализации событий. Пример: 26 событий, 15 входов, 11 выходов; даты 07.02 и 17.10.2026. Постоянный импорт и конверсия пока не включены: нет привязки счётчиков и подтверждённого покрытия. Контракт и необходимые несекретные сведения — TRAFFIC-DATA-CONTRACT.md. Открытие будущих отчётов не должно обращаться к счётчику напрямую.

## Что не менялось

Существующие API справочников Core, расписание Core и S3 сохраняются. Изменение поведения клиента Core при ошибках картинок требует отдельного обновления Core; здесь подготовлена сторона AI и CORE-IMAGE-RETRY.md. Автоматического обновления Core/сервера в этой задаче нет.
