# Причал AI v0.3.2 — чистый bootstrap Timeweb

Новая база заполняется из Saby. Старую PostgreSQL не подключаем и её данные не копируем.
Все таблицы, индексы и начальная Seller Policy из v0.3.1 сохранены в `app/db/schema.sql`.
ShiftEngine и PayrollEngine сохранены. Скрипта переноса старой БД в этой сборке нет.

## 0. Настройки перед первым запуском

Заполните переменные из `.env.example` в Bothost либо в локальном `.env`.
Нужны существующие Telegram/OpenAI/Saby настройки и новая целевая PostgreSQL.

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
DB_SCHEMA=prichal_ai
DATABASE_SSL_MODE=require
AUTO_SYNC_ENABLED=false
AUTO_SYNC_ON_START=false
BACKFILL_CHUNK_DAYS=7
BUSINESS_TZ=Asia/Yekaterinburg
S3_ENABLED=true
S3_ENDPOINT_URL=https://s3.twcstorage.ru
S3_REGION=ru-1
S3_BUCKET=<существующий бакет>
S3_ACCESS_KEY_ID=<ключ>
S3_SECRET_ACCESS_KEY=<секрет>
S3_PREFIX=prichal-ai/
```

Для проверки сертификата используйте `DATABASE_SSL_MODE=verify-full` и
`DATABASE_SSL_CA_B64` (PEM в base64) либо `DATABASE_SSL_CA_FILE`.
`require` без CA шифрует соединение без проверки сертификата.
Старые параметры `SOURCE_DATABASE_*` удалите из настроек хостинга.
Используйте пустую целевую схему. Инициализация не очищает данные: при наличии прежних фактов
выберите новую пустую схему, не запускайте reset. S3 остаётся подключённым;
bootstrap не копирует и не удаляет объекты бакета.

## 1. Создать схему

Из корня приложения в консоли контейнера:

```bash
python -m scripts.bootstrap init-db
python -m scripts.bootstrap status
```

Обычный запуск приложения также создаёт схему. Создание транзакционное;
повторный запуск сохраняет данные. Поиск таблиц ограничен DB_SCHEMA, без `public`.
После чистого init-db stores/sales/shifts равны нулю. Seller Policy v1 уже создана
как часть исходной схемы — это правило приложения. S3 должен вернуть `ok=true`, `enabled=true`.
Telegram: `/ping`, `/infrahealth`. Ожидаем `v0.3.2 | timeweb-clean-bootstrap`.
Деплой историю не загружает: оба флага auto-sync по умолчанию false.

## 2. Загрузить stores

```bash
python -m scripts.bootstrap stores
```

Либо Telegram: `/loadstores`. Загружается только справочник, без чеков и смен.
Сверьте ID, названия и число магазинов с Saby. При необходимости задайте SABY_POINT_IDS
до загрузки. Пустой список останавливает процесс. Повтор обновляет stores по point_id.
Backfill требует загруженные stores и совпадение их списка с текущим ответом Saby.
Загрузка не удаляет магазины, исключённые фильтром: задайте фильтр с самого начала.

## 3. История по неделям и reconcile

Сначала контрольная неделя:

```text
/backfill 2026-07-01 2026-07-07
/backfillstatus
```

Либо:

```bash
python -m scripts.bootstrap backfill 2026-07-01 2026-07-07
```

После сверки контрольной недели загрузите остальной диапазон, например:

```text
/backfill 2026-07-08 2026-09-30
```

Выберите нужный конец истории. Допускаются только завершённые business days.
До 08:00 по Екатеринбургу вчерашний business day ещё не завершён.
Если в Telegram указать только начало, конец — последний завершённый business day.
CLI требует обе даты и использует блоки по 7 дней; Telegram использует BACKFILL_CHUNK_DAYS.

Для каждого блока приложение:

1. Загружает календарные даты блока и ещё один день для последней ночи.
2. Обновляет sales/payments/items существующим upsert и перестраивает смены блока.
3. Выполняет исходный reconcile для каждого business day.
4. Показывает смещение целой смены между датами отдельно (см. RECONCILE_FIX.md). Сохраняет отчёт в app_meta и только при OK двигает next_date.

Критерии OK с v0.3.5: ожидаемые по платёжным фактам целые смены и сохранённые work shifts совпадают по сумме (разница <0,01 ₽)
и числу чеков; нет fallback-платежей, чеков без продавца и смен REVIEW.
`Sale − Payments` остаётся диагностикой, а не новым правилом зарплаты.
Возвраты не входят в выручку; business day остаётся 08:00→08:00.

Reconcile — внутренняя сверка, не независимое подтверждение полноты Saby.
Пустой день может пройти её: проверьте дни без продаж и итоги контрольных магазинов
по отчётам Saby с тем же окном 08:00→08:00. Ошибка API, повтор страницы или
исчерпание лимита страниц останавливают загрузку вместо признания неполного ответа успешным.

При REVIEW/ошибке сохраняются ERROR, причина и прежний next_date:

```text
/reconcile 2026-07-01
/backfillstatus
/backfillresume
```

Продолжайте после исправления причины. Resume повторно загружает проблемную неделю,
не обходит reconcile. Неустранённая неоднозначность смен продолжит блокировать загрузку.
Автоматического признания таких смен корректными нет.

```bash
python -m scripts.bootstrap reconcile-report 1
python -m scripts.bootstrap resume 1
```

Замените 1 на ID запуска. В app_meta хранится последняя проверка каждого диапазона.
После разрыва процесса повтор обновляет существующие ключи без добавления дублей.
Счётчики upsert отражают обработку, а не число уникальных записей: соседние блоки
пересекаются по дополнительному календарному дню. На границах выбранного периода
могут оставаться факты соседнего business day; завершён только диапазон backfill_runs.
Пауза в Telegram: `/backfillcancel`; после перезапуска продолжение запускается вручную.

Используйте один загрузчик: Telegram **или** CLI. Не запускайте параллельно `/sync`,
перестроение смен или reset. Второй backfill блокируется PostgreSQL.
Оба флага auto-sync должны оставаться false до завершения всех этапов.

## 4. Identity и payroll foundation

Когда весь нужный период загружен и проверен:

```bash
python -m scripts.bootstrap foundation 2
```

Укажите ID завершённого запуска. Команда заново сверяет его период, создаёт identities
из смен Saby и выводит SELLER policies. Если были несколько запусков, проверьте каждый.
Команда не подтверждает непрерывность истории между разными запусками.
Telegram-эквивалент создания identities после проверок: `/identitysync`.

Планы, дополнительные версии политик, экзамены и связи Core не копируются из старой БД.
Введите их заново по утверждённым исходным данным:

```text
/paypolicy SELLER 2026-09-19
/setplan <магазин> | DAY | ALL | <план> | 2026-09-01
/setplan <магазин> | NIGHT | ALL | <план> | 2026-09-01
/plans <магазин>
/setexam <сотрудник> | 2026-09 | PASS
/payrollpreview 2026-09-19
/payrollmonth 2026-09
```

PASS задавайте только при подтверждённом результате. Все правила и команды — в README.md.
Сохранены фикс 2 000 ₽, ступени KPI 0%/3%/5%, экзамен +3%, приоритет weekday над ALL,
версии политик по датам. KPI определяется по магазинной DAY/NIGHT-смене,
процент применяется к личной выручке. NIGHT_ASSISTANT остаётся отдельной ролью;
его смены и связи Core автоматически не создаются.

## 5. Включить регулярную синхронизацию

После проверки всего периода, заполнения foundation и контрольного расчёта:

```env
AUTO_SYNC_ENABLED=true
AUTO_SYNC_ON_START=true
```

Повторно разверните приложение; проверьте `/infrahealth` и `/reconcile` за завершённый день.
Перед включением догрузите разрыв до текущего периода: auto-sync охватывает только
SYNC_RECENT_DAYS (по умолчанию 3 дня). Для нового backfill снова отключите оба флага.

## Проверки сборки

```bash
pip install -r requirements.txt pytest tzdata
python -m pytest -q
```

Тесты используют фиктивные настройки и подмены сервисов, не подключаются к Timeweb/Saby.
Реальное подключение, права схемы, S3 и контрольную сверку проверьте при развёртывании.
