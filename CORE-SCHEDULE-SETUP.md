# График Core → AI: установка и проверка

## Что реализовано

Core v1.7.16 на основе v1.7.15 отдаёт GET /api/v1/ai/schedule?date_from=2026-10-01&date_to=2026-10-31. AI v0.3.13 на основе v0.3.12 получает график, хранит назначения в отдельной таблице core_schedule_assignments и показывает /coreschedule.

График Core считаем действительным по решению владельца. Подтверждение явки не требуется. Изменения не перераспределяют выручку, не меняют payroll и Saby-смены: эти функции будут подключены к графику отдельно.

Передаются ID назначения, ID сотрудника и магазина Core, имена, должность из карточки, business date графика, DAY/NIGHT, slot, подтверждённая связь магазина с Saby. Назначения всех должностей сохраняются как есть: номер ночного слота не превращается автоматически в роль помощника. Исторические назначения не исключаются по текущему кадровому статусу сотрудника. Телефоны и другие кадровые контакты не передаются.

В графике Core нет точного времени начала/конца — оно не выдумывается и не отправляется. Даты и DAY/NIGHT передаются без часового пересчёта. Перед будущим распределением чеков потребуется согласовать границы смен.

## Установка — сначала Core

1. Установить prichal_core_v1_7_16_schedule_export.zip в приложение Core, сохранив текущие настройки. Это полная сборка на основе последнего доступного v1.7.15; если Core уже обновлён позднее, сначала перенести изменения в ту версию, не понижать её.
2. Сохранить существующий CORE_DIRECTORY_API_KEY (не менее 32 символов), совпадающий с AI. Нового секрета не требуется.
3. В Core в «Админ → Связь с Saby» подтвердить магазины. Несвязанные магазины не теряются при экспорте: AI сохраняет их с предупреждением и saby_point_id=null. Сотрудники передаются по Core ID, привязка личной учётки Saby для загрузки графика не обязательна.
4. Перезапустить Core. На главной странице ожидается версия 1.7.16. Существующая админка и справочники сохраняются, новых таблиц Core не требуется.

## Затем AI

1. Установить prichal-ai-v0.3.13.zip и сохранить настройки Saby, PostgreSQL, S3, домена, порта и автосинхронизации продаж.
2. Задать CORE_BASE_URL — публичный HTTPS-адрес вашего Core без пути /miniapp, без параметров и без адреса API. Используется тот же CORE_DIRECTORY_API_KEY, что на Core. На первом этапе CORE_SCHEDULE_SYNC_ENABLED=false.
3. Перезапустить AI: таблица графика создастся автоматически. В Telegram /version должен показать 0.3.13.
4. В консоли AI выполнить:

```bash
python -m scripts.core_schedule sync 2026-10-01 2026-10-31
```

В результате assignments — количество полученных назначений, unmapped_core_store_ids — магазины Core без подтверждённой связи с Saby. Пустой список означает отсутствие таких проблем среди полученных назначений, а не проверку всего справочника.

5. В Telegram AI:

```text
/coreschedule 2026-10-09
```

Сравнить сотрудников, магазины и DAY/NIGHT с Core за эту дату. Для подробной проверки:

```bash
python -m scripts.core_schedule report 2026-10-01 2026-10-31
```

6. После контрольной проверки включить на AI:

```env
CORE_SCHEDULE_SYNC_ENABLED=true
CORE_SCHEDULE_SYNC_INTERVAL_MINUTES=30
```

Перезапустить. Первый запрос выполняется при старте, следующие — через 30 минут после завершения предыдущего. По умолчанию окно: от 31 дня до текущей даты до 31 дня после неё (63 дня включительно), в часовом поясе AI. Более старую историю загружать той же командой вручную, блоками не более 93 дней включительно. Исправления вне автоматического окна требуют повторной ручной загрузки нужного периода.

В логах успех: Core schedule sync completed. Ошибка: Core schedule sync failed; previous snapshot retained. Продажи Saby загружаются независимо.

## Контракт и поведение

Авторизация: Authorization: Bearer <CORE_DIRECTORY_API_KEY>. Пустой/короткий ключ выключает API (503), неверный — 401. Redirect не выполняется, ключ не передаётся в URL. Ответ содержит schema_version=1, source=prichal_core, authority=actual_schedule, complete_snapshot=true, generated_at (UTC), обе границы периода, count и shifts. Все ID — строки.

Core читает назначения, сотрудников и привязки одним SQL-запросом. Старые назначения с user_id разрешаются через Employee.user_id. Если сотрудника невозможно разрешить или тип смены неизвестен, возвращается 409 целиком, без частичной выгрузки. РЦ исключается по подтверждённому ID Saby 23109. Без связи магазина с Saby распознать РЦ по одному имени нельзя.

AI проверяет даты, ID, типы смен, число записей, отсутствие дублей и полноту ответа до записи. Применение снимка атомарное и сериализовано между CLI и фоновыми запросами. Повторное получение обновляет существующие записи по ID назначения. Отсутствующие в полном снимке назначения помечаются cancelled=true только в указанном периоде. Пустой полный снимок означает отмену всех сохранённых назначений этого периода. Записи вне периода сохраняются. Источник различается по CORE_BASE_URL: смена домена требует повторной загрузки, старые записи другого источника в отчёте не показываются.

Смена сотрудника через подмену Core обычно создаёт новое назначение и удаляет старое — снимок это отражает. При сетевой ошибке, некорректном ответе или ошибке БД предыдущий график остаётся целиком. Последняя успешная загрузка не означает отсутствие последующих ошибок; проверяйте журнал. При отменах сохраняются записи с cancelled=true, но отдельного журнала всех старых значений AI пока не ведёт — история изменений остаётся в Core.

Локальные проверки не подтверждают установку на ваши серверы. Нужна контрольная загрузка после обновления обеих сторон.
