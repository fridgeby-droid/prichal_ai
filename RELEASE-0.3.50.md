# Причал AI 0.3.50 — личные уведомления и поручения

## Включение после установки

Напишите боту **в личный чат**:
```
/notifications on
```
Это включает доставку этому пользователю. Утренний обзор — **10:00, Екатеринбург**. Настройки не активируются установкой архива: бот должен получить личную команду, чтобы сохранить подписку. Уведомления доступны только Telegram ID из существующего списка разрешённых пользователей. В группы этот пакет ничего не отправляет.

Настройки и задачи хранятся в существующей `app_meta` PostgreSQL и переживают перезапуск. Новых таблиц, миграции продаж и сторонних зависимостей нет. Цикл уведомлений запускается вместе с приложением независимо от AUTO_SYNC_ENABLED; сами данные он не загружает.

## Управление

```
/notifications
/notifications off
/notifications on
/notifications morning off
/notifications morning on
/notifications tasks off
/notifications tasks on
/notifications time 10:00
/tasks
/tasks pause ID
/tasks resume ID
/tasks cancel ID
```

То же доступно обычными фразами: «Отключи утренний обзор», «Включи проверки задач», «Присылай обзор в 11:00», «Покажи мои задачи». Общий выключатель приостанавливает отправку, не удаляет задачи; отдельные выключатели управляют обзорами и проверками. Уже начатая отправка может успеть прийти после выключения. /newdialog очищает только разговор, не поручения.

## Задачи

Пример:
> Через неделю проверь, улучшилась ли дневная смена Батумской.

Помощник находит магазин, сохраняет конкретный point_id и DAY, срок 7 дней, критерий **выручка в день** и подтверждает это в ответе. Можно явно выбрать **число платёжных записей в день**, **средний чек**, положительный процентный порог и срок 1–90 дней. Произвольные условия (прибыль, посещаемость, несколько взаимозависимых целей) не выполняются молча: нужно уточнение.

База — N последних закрытых бизнес-дней, числовые показатели фиксируются при создании. Период проверки — следующие N бизнес-дней. Например, создание 14 ноября в 10:00: база 7–13 ноября, проверка 14–20 ноября, срок 21 ноября в 10:00. При сроке не кратном 7 состав дней недели может различаться; результат это отмечает. Увеличение показателя — наблюдаемый результат, не доказательство эффекта действий.

До фиксации базы требуются локальные отметки загрузки и сверки и записи за каждый день выбранной смены. При неполной базе задача не создаётся. Если база равна нулю, процентное улучшение не определяется. Значение threshold_percent=0 означает строго положительный рост, а не «без изменения».

К сроку код сравнивает зафиксированную базу с новым периодом. При отсутствующих данных/незавершённой загрузке/сверке проверка ждёт и повторяется раз в час. Через 3 дня без достаточных данных присылает один итог «не удалось рассчитать», а не ложный вывод о падении. Результат сохраняется в задаче. Ожидание идёт по реальному сроку: после долгого отключения уведомлений старая задача с отсутствующими данными может сразу завершиться как недостаточно данных.

Задачи можно приостанавливать, возобновлять и отменять. До 30 активных задач; сохраняются последние 100 завершённых записей плюс активные. /tasks показывает активные и последние 20 завершённых. Удаление чужих задач исключено: получатель берётся из Telegram-события, инструмент не принимает произвольный ID пользователя.

## Утренний обзор

После 10:00 отправляется один обзор последнего закрытого бизнес-дня: выручка, платёжные записи, средний чек и три крупнейших наблюдаемых изменения по магазинам. База — тот же день недели неделю назад. Если текущий день ещё не загружен/не сверен, отправка ждёт, повтор проверки раз в час. Если не готова база сравнения, текущие показатели могут быть отправлены с пометкой, что сравнение недоступно. Пропуски не обозначаются нулём.

После простоя сервер не рассылает накопившиеся обзоры за каждый пропущенный день: отправляется только актуальный закрытый день. Этот релиз не включает отдельные пороговые оповещения обо всех аномалиях сети; здесь два типа доставки — утренний обзор и результаты поручений.

## Доставка и перезапуск

Планировщик проверяет очередь каждые 30 секунд, под общей PostgreSQL advisory lock. Состояние PROCESSING восстанавливается после 10 минут без завершения. Перед запросом Telegram сохраняется SENDING. При тайм-ауте отправки либо перезапуске в момент отправки — DELIVERY_UNKNOWN: автоматического повтора нет, поскольку сообщение могло дойти. Результат доступен через /tasks; состояние утренней доставки — /notifications. Гарантия exactly-once Telegram невозможна; выбрано предотвращение автоматических дублей при неопределённой доставке.

В момент выключения/отмены до стадии отправки воркер повторно проверяет настройки и статус задачи. Для доставки нужны работающий сервер, PostgreSQL и доступ Telegram. Запланированные расчёты и сообщения выполняет программный код, без вызова языковой модели. Модель используется только для понимания команды пользователя.

## Проверка после обновления

1. `/notifications` — общий выключатель выключен для нового пользователя, время 10:00.
2. `/notifications on` — включение лично себе.
3. `/notifications morning off`, затем `on` — независимое переключение обзора.
4. Создать поручение примером выше; проверить магазин, DAY, показатель, базу и срок в ответе.
5. `/tasks`, пауза, возобновление, отмена по ID — состояние меняется и не пропадает после перезапуска.
6. Поручение другого пользователя не видно и не изменяется; из группы настройка запрещена.
7. Для проверки ближайшей отправки можно временно поменять время обзора на ближайшую минуту после текущей и затем вернуть 10:00. Если обзор за этот день уже отправлен, изменение времени не отправит его повторно.

Автоматические тесты проверяют переходы состояний, фильтр смен, периоды, порог, ожидание данных, отключение, отмену и неопределённую доставку. Боевые PostgreSQL, Telegram и OpenAI в локальных тестах не используются; фактическую доставку нужно проверить после установки.
