# v0.3.25 — детальная аналитика и основа клиентских отчётов

## Реализовано

- В `/drivers` добавлены товары и категории сопоставимой сети с тем же отбором магазинов. Чтение обоих периодов и состава сети выполняется в одной транзакции. Категорийный блок доступен при сохранённом каталоге.
- При выборе магазина через point_id получаются его DAY/NIGHT, категории и товары. В товарном сравнении появились количества и средняя фактическая цена единицы; это сумма строк / количество, а не изменение прайса.
- В сравнении появляется краткая вычисляемая сводка изменения выручки за день всей и сопоставимой сети. Причины не выдумываются.
- Средние показатели сети, магазинов и учёток продавцов за период или всю **локально загруженную** историю.
- Товарные количества по ID товара, магазину, ID учётки, периоду и DAY/NIGHT. Возвратные количества отдельно, разные единицы не складываются. Отказанные строки и удалённые продажи исключены.
- Наполняемость продажи Saby: строк и разных товаров на продажу, количество на продажу отдельно по единицам. Продажи без строк явно указаны и включены в знаменатель.
- Динамика платежей по датам и дням недели; среднее по дню недели делится на все календарные вхождения этого дня, не только дни с записями. Пропуски не доказывают нулевые продажи.
- Клиенты по уже сохраняемому `Customer` / `customer_id`: наблюдаемая последняя покупка, число покупок и разных бизнес-дней с покупками, средний интервал между такими днями. Группы 0–29, 30–59, 60–89, 90+ дней; списки по 50 записей.

## Команды Telegram

```text
/avgcheck
/avgcheck 2026-09-01 2026-09-30
/avgcheck 2026-09-01 2026-09-30 seller=123
/avgcheck 2026-09-19 2026-09-19 point=5598 shift=NIGHT
/itemqty 2026-09-01 2026-09-04 query="пакет"
/itemqty 2026-09-01 2026-09-04 point=5598 seller=123 query="тара" shift=DAY
/basket 2026-09-01 2026-09-30 point=5598
/trend 2026-09-01 2026-09-30 point=5598
/clients 2026-07-01 2026-10-22 min=30 max=59
/clients min=60 offset=50
```

`seller=123` — пример, замените на реальный ID из `/avgcheck`. Идентификатор 5598 — Яблокова, не Батумская. Для Батумской сначала найдите её ID через обычный запрос боту о магазинах, затем добавьте `point=ID` к `/itemqty`. Поиск `query` возвращает все совпадающие товары отдельно: одинаковое название не является основанием склеивать их. В ответе есть стабильный ключ товара; поиск принимает числовой ID либо UUID без префикса, либо подстроку имени.

Без дат используется вся локальная история до текущей местной даты. Обе даты нужно либо указать, либо опустить. Опции `point`, `seller`, `shift`, `query`, `min`, `max`, `offset` записываются через `=`; строки с пробелами берутся в кавычки. Прямые команды не используют LLM, доступ ограничен существующим списком разрешённых пользователей.

Для клиентов верхняя дата задаёт дату отсечения, а нижняя **не ограничивает** историю поиска последней покупки. При фильтре магазина давность считается именно для этого магазина, не для всей сети. `min=30 max=59` включает 30 и 59; для строго «больше 30» используйте `min=31`. Наблюдаемая последняя покупка может быть устаревшей из-за неполной загрузки — это не доказанный отток. Клиенты без покупок в локальной истории в такой список не попадут. Фильтры продавца, смены и товара для клиентской давности запрещены.

Для товаров и клиентов переходите по `next_offset`, чтобы получить полный список, не ограничивайтесь первой страницей. Отчёт по товарам группируется одновременно по точке, учётке, ключу товара и единице.

## Средние чеки: две разные базы

1. Платёжный СЧ: невозвратная сумма платёжных записей / число невозвратных платёжных записей. Сохраняет действующее определение в Причал AI, показывает fallback. Не считается доказанным средним по уникальным фискальным чекам.
2. Средняя сумма продажи: `sales.total_price` / число невозвратных продаж с уникальным `(point_id, sale_id)`. Выводится отдельно. Не подменяет платёжную выручку.

Для сети и продавцов среднее вычисляется из сумм и количества, не как среднее средних магазинов. Возвраты отдельно. Товарные количества относятся к продавцу **продажи** и её бизнес-дате; платежи имеют свою дату и атрибуцию. DAY/NIGHT — тип смены в данных, не реальный график Core и не конкретный ID кассовой смены. Работа под чужой учёткой не исправляется предположениями.

## Бонусы, карты и модификаторы — ещё не включены в расчёты

Исходные ответы продаж и строк уже сохраняются в `raw_json`. Новая сборка не заявляет нормализованный реестр карт, бонусных операций или проданных модификаторов. `customer_id` не доказывает наличие карты. Скидка не считается списанием бонусов. Средний чек «с картой» и доля бонусов в выручке пока недоступны, а не равны нулю.

Подтверждённый владельцем пример: **продажа 25522**, **Шоссе Космонавтов 115а**, **23.10.2026 16:22**, **9 баллов начислено**, **1 тара 1 л**. После установки выполните:

```text
python -m scripts.diagnose_sale 25522
```

Команда читает локальный `raw_json`, выводит пути полей и типы, скрывает все строковые значения, номера карт, телефоны, имена и произвольные ключи. Числовые значения выводятся только для узкого списка полей количества/бонусных сумм. Если `sale_id` встретился в нескольких точках, команда вернёт `AMBIGUOUS` и ID точек: повторите с `--point-id ID`. Если `NOT_FOUND`, дождитесь загрузки этой продажи; произвольная повторная загрузка всей истории не нужна.

Нужен результат этой команды, чтобы проверить реальные поля источника. Подтверждение только начисления 9 баллов не подтверждает формат списания; для списаний потребуется аналогичный пример продажи. Исторический остаток нельзя восстанавливать лишь как начислено минус списано без начального баланса, истечений и ручных корректировок.

Следующее продолжение после диагностики: определить стабильные ID клиента/карты/операции, нормализовать подтверждённые начисления, списания и модификаторы с родительской строкой; обеспечить повторный импорт без дублей и замену исправленных фактов. Затем добавить средние покупок с картами/без карт, долю списаний с явным знаменателем и текущие остатки при наличии проверенного источника. Не выводить модификаторы продажи из настроек каталога: настроенный модификатор не означает, что он был продан.

Официальные ссылки для проверки контракта:
- [API бонусов Saby](https://saby.ru/help/integration/api/app_sale/sale_bonuses) описывает работу с бонусами, но не подтверждает состав нашего сохранённого ответа продажи.
- [Каталог с модификаторами](https://saby.ru/help/integration/api/app_sale/sale_delyvery/catalog) описывает каталог, а не фактически проданные количества.

## Серверная команда и инструмент AI

```text
python -m scripts.detail_report quantities --start 2026-09-01 --end 2026-09-04 --query "пакет"
python -m scripts.detail_report averages
python -m scripts.detail_report clients --min-days 30 --max-days 59
```

Агенту доступен `get_detail_report`. Все расчёты выполняет код, LLM получает числа и готовый текст. Новые детальные отчёты сообщают последний sync и неподтверждённую полноту; они не выполняют сверку автоматически. Даты проверки смотрите в `/reportquality` и прежних управленческих отчётах. Клиентские списки содержат ID, без телефонов и контактов. Рассылок нет.

Продажи, позиции и customer_id уже находятся в БД; новая сборка читает их, не создаёт отдельную полную клиентскую CRM. Миграция и новые секреты не требуются. Рабочая БД и сервер при подготовке архива не изменялись. Установка и проверка на настоящих данных выполняются отдельно.
